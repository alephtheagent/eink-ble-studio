# BLE pages protocol v1

The existing service `7b1e0001-6ba2-4f25-8ac7-1d54e91a1000`, v1/v2 frame endpoints and DFU remain unchanged. Pages use `7b1e0007-6ba2-4f25-8ac7-1d54e91a1000` (command, WRITE with response), `7b1e0008-6ba2-4f25-8ac7-1d54e91a1000` (status, READ, exactly 20 bytes), and `7b1e0009-6ba2-4f25-8ac7-1d54e91a1000` (data, READ, variable length). Integers are little endian. All commands fit MTU 23 except DATA and ORDER_DATA, whose payload is bounded by the negotiated ATT write limit; minimum MTU 23 is supported. One GATT operation at a time; write, then poll status until pending clears, checking opcode, error and exact acknowledgement before continuing. ATT write success is not storage success.

Status is `version:u8=1, op:u8, error:u8, flags:u8, collectionRev:u32, id:u32, pageRev:u32, value:u32`. Flag bit 0 means pending: poll until clear; all other bits reserved zero. While pending no new command is accepted. Errors: 0 OK, 1 malformed, 2 busy, 3 not found, 4 conflict, 5 full/exhausted, 6 CRC, 7 storage, 8 offset, 9 padding. A successful mutation is reported only after the new metadata has been written, verified and committed. A failed or lost response may leave the operation committed; reconnect and inspect INFO/LIST and CRC before retrying. Never assume an entire multi-operation sync is atomic.

| Opcode | Command | Result after completion |
|---|---|---|
| 01 | INFO | id=count, pageRev=maximum count, value=free physical frame slots |
| 02 | LIST index:u16 | id=stable page ID, pageRev=page revision, value=frame CRC32; index is zero based |
| 03 | READ id:u32 offset:u16 | id/pageRev identify page; value=full frame CRC32. Read data characteristic next: offset:u16 followed by up to 18 bytes; offset 4000 returns only offset (EOF). |
| 04 | BEGIN expectedCollectionRev:u32 id:u32 expectedPageRev:u32 crc:u32 | Begin raw 4000-byte upload; id=0 creates, expectedPageRev=0. Result id is reserved new stable ID, pageRev is current revision (0 for creation), value=0. |
| 05 | DATA offset:u16 payload | Sequential raw bytes; nonempty payload. value=exact next byte offset. |
| 06 | COMMIT | Verify 4000 bytes, CRC and padding; durable COW commit. id=new/existing stable ID, pageRev=new revision, value=CRC. |
| 07 | DELETE expectedCollectionRev:u32 id:u32 expectedPageRev:u32 | Durable delete; id=deleted ID. |
| 08 | BEGIN_ORDER expectedCollectionRev:u32 count:u16 | Start reorder, count must equal current count and not exceed advertised capacity; value=0. |
| 09 | ORDER_DATA index:u16 ids:u32[] | Nonempty integral IDs, sequential index measured in IDs, not bytes; value=exact next index. |
| 0A | COMMIT_ORDER | Validate permutation and expected collection revision; commit order durably. |
| 0B | ABORT | Discard uncommitted upload or reorder; committed data is untouched. |
| 0C | SHOW id:u32 | Queue the stored page for panel refresh; completion indicates accepted, not an optical check. |

Frame layout is the existing 122×250, 16-byte stride, 4000-byte format; low six bits of each row's last byte must be zero. CRC is IEEE CRC32 over all 4000 bytes. Every committed mutation advances collectionRev; page update advances that page's revision, while reorder does not. Revision and ID exhaustion fail closed; stable IDs are never reused. BEGIN reserves the next ID without committing it: after a lost COMMIT acknowledgement, identify the result by the BEGIN ID and LIST/CRC. If disconnected before commit the reservation may be reused. Expected revisions are rechecked at COMMIT, not merely BEGIN. Conflict means reread the collection and reconcile, not blind overwrite.

Every status carries collectionRev. For a consistent snapshot, obtain INFO, LIST each index, READ each frame in offsets advancing by the returned payload length, verify the full frame CRC, then INFO again; discard and retry if any status or final INFO has a different collectionRev. READ selects a shared data characteristic, which must be read before the next command. The deployed firmware supports **one connected central only**: `Bluefruit.begin()` uses the pinned core's defaults `prph_count=1, central_count=0`, configured as the SoftDevice peripheral role and connection counts. Multiple independent concurrent centrals, or multiple clients interleaving commands over one connection, are not supported; host endpoint tests do not establish such support. Serial operations and revision checks prevent accepting a torn snapshot, and the CRC checks each complete frame.

A disconnect aborts uncommitted transfers; a pending commit may finish durably. The owning connection must not interleave another command while a transfer is active, and the legacy frame/display path is blocked while shared display/transfer state is in use. While a queued page is waiting for the panel driver (`SHOW` accepted but not yet rendered), every other command returns `busy`; only continuation of the already active upload or order operation is accepted, so its in-memory frame cannot be overwritten before the driver copies it. Invalid commands never alter committed metadata. If the server configuration is ever changed to permit multiple centrals, the shared READ selection requires explicit per-connection ownership before that configuration is safe.

The application reserves `0xCC000..0xEBFFF` (exclusive end `0xEC000`), 32 erase sectors of 4096 bytes. Two sectors are alternating metadata banks; 30 are frame slots, of which one must stay free for copy-on-write, hence at most 29 live pages. Recovery chooses the newest valid committed metadata bank after checking CRCs and all referenced frames. A write erases only an unreferenced slot, verifies the frame, writes the alternate metadata bank and programs its commit marker last. Interrupted mutations recover the old or new complete collection, not a partially updated one. A full device still supports one replacement using the spare. Repeated writes wear internal flash; avoid unchanged writes. Flash failure and exhaustion are reported, never silently discarded.

This reservation shortens the application linker region and must fit the actual image. The existing welcome sector is `0xEC000..0xECFFF`, and the core internal filesystem begins at `0xED000`. Actual installed nice!nano bootloader and update behavior are not verified on a physical device; neither UF2 nor BLE OTA preservation of pages is guaranteed. **Back up pages before any firmware update** and retain a USB recovery path.
