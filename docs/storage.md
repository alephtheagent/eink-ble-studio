# Page storage and flash map

This map is for the project's nRF52840 S140 6.1.1 configuration, not a verified dump of the installed board. All ends below are exclusive; erase sectors are 4096 bytes.

| Range | Use / evidence |
|---|---|
| `0x00000..0x26000` | SoftDevice; application origin is set in `firmware/eink_s140_v6.ld`, and S140 6.1.1 in `firmware/boards/promicro_nrf52840_s140v6.json`. |
| `0x26000..0xCC000` | Application FLASH, 0xA6000 = 679936 bytes maximum; linker rejects overflow. |
| `0xCC000..0xCE000` | Two metadata banks. |
| `0xCE000..0xEC000` | Thirty 4 KiB frame slots; at most 29 live frames, retaining a COW spare. Each 4000-byte frame occupies one slot. |
| `0xEC000..0xED000` | Existing welcome record (`firmware/include/boot_state.h`). |
| `0xED000..0xF4000` | Seven-sector InternalFileSystem: pinned core `libraries/InternalFileSytem/src/InternalFileSystem.cpp`, `LFS_FLASH_ADDR` and `LFS_FLASH_TOTAL_SIZE`. |
| `0xF4000..0x100000` | Core's nRF52840 bootloader boundary (`libraries/InternalFileSytem/src/flash/flash_nrf5x.c`, `BOOTLOADER_ADDR`); board profile identifies settings at `0xFF000`. Actual installed bootloader/version/layout is unverified. |

The [nice!nano manufacturer documentation](https://nicekeyboards.com/docs/nice-nano/#bootloader) says it uses the Adafruit nRF52 bootloader and links a 0.6.0 S140 6.1.1 image. This does not establish what is installed on a particular device. The [Adafruit bootloader repository](https://github.com/adafruit/Adafruit_nRF52_Bootloader) supports UF2 and DFU; neither those general facts nor the application's linker bounds prove that an installed version preserves this new region through either update method. Application UF2 blocks do not deliberately include pages, but updater erase and staging behavior remain unverified. **Export/backup every page before UF2 or OTA updates**, and maintain a USB recovery path. No physical flashing or retention test is claimed.

For a concrete upstream reference, Adafruit bootloader [0.6.0 `linker/nrf52840.ld`](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/0.6.0/linker/nrf52840.ld) places bootloader code at `0xF4000`, configuration in the final 2 KiB below `0xFE000`, MBR parameters at `0xFE000`, and bootloader settings at `0xFF000`; UICR records bootloader and MBR parameter addresses. This upstream layout is evidence about that source version, not identification of the bootloader on the target.
The host-testable `firmware/include/page_storage.h` takes an injectable flash interface with absolute-address `read`, `program`, and `erase`. Each metadata bank stores generation, collection revision, next ID, ordered IDs/page revisions/slot addresses/CRCs, its own CRC, and a final commit marker. To replace a frame, erase only a slot not referenced by the current bank, program and read/CRC verify the frame, erase and write the alternate metadata bank, verify its content, then program and verify its marker. Recovery chooses the newer valid bank after checking metadata and every referenced frame CRC. Power interruption may yield the old or the new committed operation; no promise is made that an entire multi-page synchronization is atomic. Invalid metadata is not reformatted. An interrupted first metadata commit can recover an empty collection when the other bank is erased and neither bank has a committed marker. Physical read failures are errors, not a format request.

On target, flash operations occur in the application loop after `Bluefruit.begin()`: erase uses the pinned core's SoftDevice-aware `flash_nrf5x_erase`; programming uses `sd_flash_write` and the Bluefruit SoC flash event, with marker as a separate word write. Core `flash_nrf5x_write` is intentionally not used because its page cache can erase/rewrite a whole sector. BLE callbacks never perform flash operations. Per-update erases consume endurance: callers should compare revisions and CRCs and send only changed pages. Storage exhaustion, revision/ID exhaustion, CRC errors and flash failures are reported. The 29-page bound is a consequence of the reserved sector count, not an estimate of the total chip capacity.

The page programmer suspends FreeRTOS scheduling across `sd_flash_write` acceptance and publication of the callback owner, leaving SoftDevice interrupts enabled. If S140 reports BUSY, `FLASH_WAIT_OTHER` routes the previous operation's completion to the core callback before waking the page programmer to retry; only an accepted page write uses `FLASH_PAGE`. The source buffer remains live until the completion event, with no timeout that could release an in-flight buffer. Application flash writes are initiated in the main loop, but the pinned Bluefruit core also has bonding/InternalFS paths, so this routing does not assume that all SDK flash activity originates there. The actual event routing and timing have not been verified on hardware.

Navigation has a GPIO-independent selector in `firmware/include/page_navigation.h`; no physical buttons or encoder pins are assigned. Existing welcome handling is unchanged: normal boot with a valid welcome record does not initialize or refresh the panel. The page protocol and snapshot/resume procedure are documented in [protocol-pages.md](protocol-pages.md).
